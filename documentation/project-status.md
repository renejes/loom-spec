# loom-spec — Project Status

## Goal

`loom-spec` is a lightweight tool that keeps a **node-based architectural spec** alongside the code of a project, inside the repo itself. It is designed to be edited by both humans (through a browser-based node editor) and AI coding agents (directly via JSON files).

The core idea: instead of describing app structure in prose, in stale diagrams, or letting it live only in the model weights of a coding agent, keep it as a **structured, machine-readable, git-diffable** set of nodes and edges. Humans see and edit it visually; agents read it before implementing and update it as code changes.

It is **a spec layer, not an execution layer**. The nodes don't run — they describe.

## Where it lives

- **`.loom/`** in the user's repo holds the data — diagram files, node-type definitions, README.
- **`.claude/skills/loom-spec/SKILL.md`** in the user's repo tells coding agents (Claude Code et al.) when and how to maintain the spec.
- **`loom-spec`** npm package provides the browser viewer/editor (via `loom-spec view`) and a scaffolder (`loom-spec init`). Nothing of the package itself is committed to the user's repo.

## Architecture

### Data model

The single source of truth is JSON files in `.loom/`. Two file kinds:

- **`.loom/node-types.json`** — declares the available node type vocabulary for the project (defaults plus user-extensible). Each type has color, icon, fields (typed: string/number/boolean/enum/markdown/code-ref/array), and optional named ports (in/out).
- **`.loom/diagrams/*.flow.json`** — one diagram per file. Each diagram is `{ nodes, edges, groups }`. Nodes carry `id`, `type`, `label`, `position`, `status` (planned/implemented/stale/deprecated), `code_refs` (path + symbol), `properties` (typed by the node's type), `tags`, optional `drill_down` (points to another diagram). Edges carry `from`, `to` (optionally with `:port` suffix), `kind` (request/event/data-read/data-write/signal/dependency/control), `label`, `direction`. Groups can nest (via `subgroups`) and can `drill_down` like nodes.

The schemas (`packages/loom-spec/schema/`) are JSON Schema Draft 2020-12. TypeScript types are autogenerated from them via `json-schema-to-typescript`, so the runtime validator (ajv) and compile-time types stay aligned.

### Server (`src/server/`)

- **Hono** on Node, port 7777 in prod (7778 during dev so Vite can own 7777).
- `findLoomRoot` walks up from CWD to locate the closest `.loom/`.
- `fileOps` reads/writes diagram and node-types files. Writes are deterministic 2-space-indented JSON with trailing newline.
- `app` exposes:
  - `GET  /api/root` — paths
  - `GET  /api/node-types`
  - `GET  /api/diagrams` — summary list
  - `GET  /api/diagrams/:id`
  - `PUT  /api/diagrams/:id` — validates against the diagram schema before writing; returns 422 with detailed errors on failure
  - `GET  /api/events` — Server-Sent Events stream
- `watch` wraps `chokidar` to detect external edits to `.loom/`. Writes triggered by our own PUT endpoint are suppressed for 1.5s so the UI doesn't react to its own saves.

### View (`src/view/`)

- **Vite + React + @xyflow/react**.
- `state.ts` holds the diagram in client state, subscribes to `/api/events` via `EventSource`, and applies external changes unless the user has an unsaved local edit (then the incoming change is dropped, not clobbered).
- All edits route through mutator helpers (`updateNode`, `addNode`, `deleteNode`, `updateEdge`, `addEdge`, `deleteEdge`). Each mutation flips `saveStatus` to `dirty`, then a 500ms debounce window flushes the whole diagram with a PUT. UI shows the status as `unsaved` → `saving…` → `saved`.
- `DiagramCanvas` converts the loom diagram into xyflow's node/edge shape, wires `onNodesChange` (positions + delete), `onEdgesChange` (delete), `onConnect` (create new edge with default kind `request`), and `onSelectionChange`.
- `Inspector` is form-driven and reads node-type fields from `node-types.json`. It renders the correct widget per field type (input / number / checkbox / select / textarea). Edges have their own panel with kind, label, description.
- Theme (`light` | `dark`) is set on `<html data-theme>` before paint to avoid flash, persisted to localStorage, toggled from the top bar.

### CLI (`src/cli/`)

- `loom-spec init [--path <dir>] [--force]` copies `templates/` into the target. Refuses to clobber an existing `.loom/` unless `--force`.
- `loom-spec view [--root <dir>] [--port <n>] [--dev]` starts the Hono server. In `--dev`, the SPA is served by Vite; otherwise Hono serves the built bundle from `dist/view/`.
- Subcommand dispatch lives in `src/cli/index.ts` with a small arg parser.

### Skill integration

The `loom-spec` skill (shipped in `templates/.claude/skills/loom-spec/SKILL.md`) follows the cross-tool Agent Skills convention. Its description triggers on architecture/component/service/data-flow keywords. The body tells the agent:

1. Read the relevant diagram before implementing.
2. Add new components as `status: planned`, flip to `implemented` after the code lands.
3. Always populate `code_refs`. Prefer `symbol` over `lines` because symbols survive refactors.
4. On code deletion, set `status: stale` — don't remove nodes silently; humans review.
5. Don't invent node types — extend `node-types.json` first.

The skill is project-scoped, lives in the user's repo, and is committed alongside the spec it governs.

## How it works in practice

### User opens the editor

1. From the user's project root: `npx loom-spec view` (would be — currently `pnpm dev` in our workspace).
2. CLI finds the nearest `.loom/`, starts Hono + chokidar watcher.
3. Vite serves the SPA (dev) or Hono serves the prebuilt bundle (prod).
4. Browser loads, fetches `/api/diagrams/overview` + `/api/node-types`, opens an `EventSource` to `/api/events`.

### User edits a node

1. Click selects → Inspector form populates from the node.
2. Type into Label field → React state mutates the diagram optimistically → React Flow re-renders.
3. 500ms after the last keystroke, the full diagram is PUT to `/api/diagrams/overview`.
4. Server validates against the schema, writes the file deterministically, records the write in the watcher's self-write map (1.5s suppression).
5. chokidar sees the file change but ignores it (suppression window). No SSE event.
6. UI flips save status to `saved`.

### Agent edits the file directly

1. Agent runs Edit/Write on `examples/todo-app/.loom/diagrams/overview.flow.json`.
2. chokidar fires; it is not a self-write, so a `diagram-changed` SSE event goes out.
3. UI's EventSource receives the event. If no local edit is pending, it refetches the diagram and updates state.
4. New label / new node / changed status appears in the canvas without a reload.

### User creates a new node

1. Top bar "+ Add" → dropdown shows the types from `node-types.json`.
2. Click a type → new node with `status: planned`, `label: "Untitled"`, default position, empty code_refs, selected in the Inspector.
3. Debounced save fires.

### Drift handling

- A node's `code_refs` may point to files/symbols that no longer exist. The agent's responsibility (per SKILL.md) is to mark such nodes `status: stale` rather than delete.
- We do not yet have automated drift detection that crawls `code_refs` and verifies them — see next-steps.

## What is verified working

End-to-end during development:

- Schema validates the example diagram.
- TypeScript types are generated and the entire codebase typechecks cleanly.
- The viewer renders 5 nodes + 5 edges from the example with correct type colors, status visuals, edge kinds, and groups.
- Light and dark themes both render correctly and persist across reloads.
- Edit a node label → file on disk reflects the change within ~500ms.
- Add a node via the "+ Add" menu → appears in canvas, persists, file gets a new entry.
- PUT with an invalid payload → 422 with descriptive errors.
- External edit (simulated via a shell script writing the JSON) → UI updates without a reload.
- `loom-spec init` writes 4 template files into a fresh directory; both scaffolded files validate against the schemas.

## What is not yet verified

- Production build path (`pnpm build` → `loom-spec view` serving the built SPA without Vite). The wiring is in place in `cli/view.ts`'s `serveSpaFrom` branch but hasn't been exercised.
- npm-installed flow (`npx loom-spec init` in a directory outside this monorepo).
- SSE behavior across a server restart (no reconnect logic on the client).
- Concurrent edits from two browser tabs against the same diagram.
- Behavior of very large diagrams (we've only tested 5 nodes).
