# loom-spec

> A node-based architecture spec that lives in your repo. AI-readable, AI-writable, git-diffable.

[![npm](https://img.shields.io/npm/v/loom-spec.svg)](https://www.npmjs.com/package/loom-spec)
[![license](https://img.shields.io/npm/l/loom-spec.svg)](LICENSE)

`loom-spec` keeps a structured visual map of your application's architecture **inside your repo**, edited by both humans (in a browser-based node editor) and AI coding agents (directly via JSON files or MCP tool calls).

It is a **spec layer**, not an execution layer. The nodes describe; they don't run.

---

## The idea

Three problems this is built to solve:

1. **Architecture drift.** Mermaid diagrams in `docs/` go stale the moment someone refactors. Whiteboard photos are write-only. Most teams have *some* picture of how their app fits together — and most of those pictures are wrong.
2. **Coding agents losing the forest for the trees.** An agent reading `src/server/routes/todos.ts` doesn't see the system; it sees one file. It can grep around, but every session rebuilds the mental model from scratch.
3. **The mental-model gap.** People who think in signal flow but don't read code well (designers, PMs, founders) get cut out of architectural conversations. Prose docs paper over this; node graphs don't.

The bet: keep one canonical, machine-readable file-set under `.loom/` that describes **what exists and how it connects**. Edit it visually. Let the agent read it before implementing and update it as code changes. Keep `code_refs` so the diagram is anchored to actual source, not just vibes.

It is deliberately **a spec, not a runtime**: nodes don't execute, edges don't carry data. Tools like Flyde or n8n run flows; `loom-spec` describes them. Different layer.

## What you get

- **Browser editor** with light/dark theme. Drag, click-to-edit-fields, debounced auto-save. Custom node types with declared ports. Group frames with drill-down navigation to sub-diagrams. Parallel-edge routing so labels don't collide.
- **Live sync**: an external edit to the JSON (e.g. by an agent) propagates to the open UI without reload, via Server-Sent Events.
- **Schema-validated** JSON Schemas (Draft 2020-12) for both diagram and node-type files, with autogenerated TypeScript types.
- **Drift detection** via `loom-spec validate` — walks every `code_refs`, checks the file exists and the symbol resolves. Exit code is non-zero on findings, suitable as a pre-commit hook or CI step.
- **MCP server** with 10 semantic tools so agents can `loom_add_node`, `loom_mark_stale`, `loom_validate`, etc. instead of re-parsing and rewriting JSON on every change.
- **Cross-tool skill**: shipped `SKILL.md` follows the [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) open standard, with five worked examples.

## Quickstart

```bash
# In your project root
npx loom-spec init --mcp      # scaffolds .loom/ + .claude/skills/loom-spec/ + .mcp.json
npx loom-spec view            # opens the editor on http://localhost:7777
```

After that:

- Drag nodes, edit fields in the inspector, save is automatic.
- Open Claude Code (or any MCP-capable agent) — it'll discover both the skill and the MCP server. Ask it to "add a payments service to the overview". It calls `loom_add_node`, the diagram updates in your browser without reload.
- Run `npx loom-spec validate` before committing to catch refs pointing at code that no longer exists.

## A typical workflow

You decide to add a payments service. Either:

**Human-first**

1. Open the editor, click **+ Add** → **Service**.
2. Label it "Payments", description "Stripe wrapper", status `planned`.
3. Drag from the existing checkout node to the new payments node → edge created with `kind: request`.
4. Implement the code.
5. Back in the inspector, set status to `implemented`, add a `code_ref` pointing at `src/server/payments.ts#chargeCard`.

**Agent-first**

1. Tell Claude Code: "add a payments service that handles Stripe charges".
2. The skill kicks in; the agent reads the overview, picks the right type, calls `loom_add_node` and `loom_add_edge`.
3. Your open editor refreshes to show the new node.
4. Agent implements the code, calls `loom_update_node` to flip status to `implemented` with `code_refs`.
5. You see the change in real time. Either confirm or push back ("call it CheckoutPayments instead").

Both paths produce the same diff in `.loom/diagrams/overview.flow.json`. Reviewing the change is reviewing a structured JSON diff, not a prose paragraph.

## What's in `.loom/`

```
.loom/
├── README.md
├── node-types.json          The node-type vocabulary for this project.
└── diagrams/
    └── overview.flow.json   { nodes, edges, groups }
```

Nodes have `status` (planned / implemented / stale / deprecated), `code_refs`, custom `properties` defined by their type, optional `drill_down` to a sub-diagram, optional `ports` for typed connections. Edges have `kind` (request / event / data-read / data-write / signal / dependency / control). Groups bundle nodes and can also drill down.

For the full format reference, see the [package README](packages/loom-spec/README.md) and the [JSON Schemas](packages/loom-spec/schema/).

## When it's not for you

- **You want a runnable flow engine** — use Flyde, n8n, Langflow.
- **You have one file you want to document** — a code comment is faster.
- **You don't have AI coding agents in the loop** — the spec still works, but the "agent maintains the diagram alongside the code" loop is the main payoff. Without it, this is a fancier diagrams-as-code with a nicer editor.
- **You distrust auto-generated docs** — note that `loom-spec` is not auto-generated from code. It's authored, by humans or by agents that read and write it explicitly.
